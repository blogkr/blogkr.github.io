## 따라 만들면서 시작합니다

지난 편에서 배경 하나에 하루를 썼습니다. 이번 편부터는 진짜 게임을 만듭니다.

참고하는 게임은 **그로우 캐슬(Grow Castle)** 입니다. 왼쪽에 성이 있고, 층마다 유닛을 세우고, 오른쪽에서 몹이 걸어오면 막아내는 게임이죠. 처음부터 내 걸 만들기보다 이미 잘 만들어진 걸 따라 해보기로 했습니다. 따라 하다 보면 "이건 왜 이렇게 돼 있지?"라는 질문이 생기고, 그 답을 찾는 게 결국 공부가 되니까요.

이번 편이 딱 그런 얘기입니다. 그로우 캐슬이 왜 그렇게 만들었는지, 저는 직접 다르게 해보고 나서야 알았습니다.

## 1. 배경은 앞뒤로 나눴다

배경 한 장 위에 몹을 올리면 몹이 그림 위에 스티커처럼 붙어 보입니다. 다리 위를 걷는 게 아니라 다리 그림 위에 떠 있는 느낌이죠.

그래서 배경을 앞뒤로 나눴습니다.

| 파일 | 역할 |
| --- | --- |
| back_04_1280x720.png | 뒤 배경 (하늘, 땅, 다리 전체) |
| bridge_front_with_grass_1280x720.png | 앞 다리 난간과 풀 |
| road_rock_front_1280x720.png | 앞쪽 바위 |

세 장 모두 같은 크기의 투명 PNG라 같은 위치에 겹쳐 놓기만 하면 됩니다. 순서는 고닷의 z_index로 정합니다. 숫자가 클수록 위에 그려져요.

[사진: 몹이 앞뒤 다리 사이에 있는 스크린샷]

몹끼리도 앞뒤가 있습니다. 몹은 세 줄(레인)로 나눠 걸어오는데, 화면 아래쪽 레인이 더 가까우니 위쪽 몹을 가려야 자연스럽습니다. 그래서 레인 번호를 z_index에 더했습니다.

```gdscript
mob.z_index = 3 + lane   # 위 3, 중간 4, 아래 5
```

## 1-1. 이 글 쓰다가 버그를 찾았다

원래는 레이어를 이렇게 잡아 뒀습니다.

| 대상 | 기존 z_index |
| --- | --- |
| 뒤 배경 | 0 |
| 몹 (위/중/아래) | 1 / 2 / 3 |
| 성 | 3 |
| 앞 배경 | 10 |

글로 정리하려고 표를 만들고 나니 이상한 게 보였습니다. 몹이 걷는 길은 성보다 화면 아래쪽, 즉 성보다 **앞**에 있습니다. 그런데 성이 3이면 위쪽 레인과 중간 레인 몹(1, 2)은 성에 붙는 순간 성 **뒤**로 들어가 버립니다. 지금은 성이 격자와 아이콘뿐이라 티가 안 났을 뿐, 성 그림이 들어가면 바로 보였을 문제였어요.

그래서 순서를 다시 잡았습니다.

| 대상 | 수정 후 z_index |
| --- | --- |
| 뒤 배경 | 0 |
| 성 | 1 |
| 유닛 | 2 |
| 몹 (위/중/아래) | 3 / 4 / 5 |
| 화살, 원거리 몹 투사체 | 6 |
| 앞 배경 | 10 |

여기서 하나 걸리는 게 있었는데, 고닷의 z_index는 기본적으로 **부모 값에 더해지는 상대값**입니다. 유닛은 성의 자식이라 유닛에 2를 넣으면 실제로는 성 1 + 2 = 3이 되어 위 레인 몹과 겹칩니다. 그래서 유닛에는 1을 넣어야 실제로 2가 됩니다.

기록하려고 표를 만들다 버그를 찾은 셈이라, 개발일지를 쓰는 이유가 하나 더 생겼습니다.

## 2. 성 그리드: 4×4, 4×5를 거쳐 3×4로

지금 성은 **가로 3칸, 세로 4층** 입니다. 그로우 캐슬과 같은 숫자인데, 처음부터 이렇게 한 건 아니었습니다.

**처음엔 속성별로 한 줄씩 배치하려 했습니다.** 속성을 4개로 잡았고, 한 줄에 한 속성을 두는 구조였어요. 그래서 4×4로 시작했습니다. 그런데 계획상 무속성도 필요했습니다. 마을에서 속성 건물을 지으면 그 속성으로 전직하는 방식이라, 기본 상태인 무속성이 빠질 수 없었죠. 그러면 5줄이 되고 5×5가 됩니다.

**문제는 화면 크기였습니다.** 배경 크기는 정해져 있으니, 칸이 늘어날수록 유닛이 작아집니다. 원래도 큰 유닛이 아닌데 거기서 더 줄면 뭐가 뭔지 구분이 안 됩니다.

**4×5도 해봤습니다.** 화살이 많이 날아가는 건 보기 좋았는데, 밸런스가 맞지 않았어요. 나중에 후방에 공격력 약한 궁수를 15명까지 둘 생각인데, 성 위가 이미 강하면 그 궁수들이 의미가 없어집니다.

**성 그림에 맞춰 배치하는 것도 해봤습니다.** 격자 없이 성을 먼저 그리고, 성 윤곽을 따라 자리를 정하는 방식이요. 성 가운데 몇 명, 좌우에 몇 명, 반대편 탑 위에 몇 명.

[사진: 처음 구상했던 그림. 성 윤곽을 따라 유닛이 서 있고, 왼쪽 땅에는 후방 궁수들이 모여 있다. (AI로 만든 콘셉트 이미지)]

[사진: 같은 구상의 게임 화면 캡처]

보기엔 제일 자연스러웠습니다. 그런데 이러면 성 그림이 바뀔 때마다 배치 좌표를 전부 다시 잡아야 합니다. 그림 수정이 곧 코드 수정이 되는 구조라 오래 못 갑니다.

결국 3×4로 돌아왔습니다. 그로우 캐슬이 처음부터 이걸 계산하고 만든 건지, 해보다가 얻어걸린 건지는 모릅니다. 그래도 아마 전자겠죠. 오래 살아남은 잘 만든 게임이니까요. 적어도 저는 두 방식을 다 해보고 나서야 격자가 제일 단순하고 오래 버틴다는 걸 알았습니다.

## 3. 클릭 배치: 칸에 역할을 정하지 않는다

유닛은 빈 칸을 클릭하면 배치됩니다. 이것도 그로우 캐슬과 같습니다.

드래그로 옮기거나 칸마다 "여긴 궁수 자리" 같은 역할을 정하는 방법도 있지만, **칸에 역할을 정하는 순간 성 그림에 맞춰 배치하던 방식과 똑같아집니다.** 유닛은 계속 늘어날 거고, 어느 칸에 누구를 둘지는 플레이어가 정하는 게 맞다고 봤습니다.

핵심 코드는 마우스 위치를 칸 번호로 바꾸는 부분입니다.

```gdscript
func _cell_at(local_pos: Vector2) -> Vector2i:
    var cell := Vector2i((local_pos / cell_size).floor())
    if cell.x < 0 or cell.y < 0 or cell.x >= grid_size.x or cell.y >= grid_size.y:
        return Vector2i(-1, -1)   # 성 밖 클릭
    return cell
```

클릭한 좌표를 칸 크기(64×70)로 나누고 내림하면 몇 번째 칸인지 나옵니다. 범위 밖이면 (-1, -1)을 돌려주고 무시합니다. 격자 크기는 grid_size 하나로 정해지니, 칸 수를 바꿔도 이 함수는 손댈 필요가 없습니다. 4×4에서 4×5, 다시 3×4로 오가는 동안 이 부분은 한 번도 안 고쳤습니다.

[사진: 클릭으로 유닛을 배치한 화면]

## 정리

| 해본 것 | 결과 |
| --- | --- |
| 속성별 한 줄 배치 (4×4 → 5×5) | 칸이 늘어 유닛이 너무 작아짐 |
| 4×5 | 화살은 많지만 밸런스 붕괴 |
| 성 그림 기반 배치 | 그림 바뀔 때마다 좌표 재작업 |
| **3×4 + 클릭 배치** | ✅ 현재 |

미리 정해두는 방식을 하나씩 걷어내니 가장 단순한 형태만 남았습니다.
